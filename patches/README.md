# Patch series

Applied in order to the pinned Wine source (`inputs.json`, `crossover-sources`). The build stops if a
patch does not apply exactly (no fuzz, no rejects). Each patch keeps its own header. A patch that
upstream ships is removed here in the change that moves the pinned source.

| Patch | From | Why mavrik needs it |
|---|---|---|
| `0001-use-the-real-user-name.patch` | [highball-engine](https://github.com/gauthierpiarrette/highball-engine) | CrossOver names every Windows user "crossover"; mavrik's existing game folders use the Mac user's name, and saves live under it, so without this a game would lose sight of its saves. |
| `0002-wined3d-auto-renderer-opengl-first.patch` | [highball-engine](https://github.com/gauthierpiarrette/highball-engine) | CrossOver picks Vulkan (MoltenVK) first for Wine's own Direct3D; mavrik's Direct3D 9 and 32-bit games were tested on OpenGL, the upstream Wine default, and stay on it. |
| `0003-mavrik-engine-identity.patch` | this repository | The CrossOver tree presents the loader as CrossOver (bundle identifier `com.codeweavers.CrossOver.wineloader`, shared with CrossOver and Apple's Game Porting Toolkit) and sends crash reports to CodeWeavers. This engine is not CrossOver: the loader becomes `org.mavrik.engine` (each game's own name stays in its app menu), the crash dialog links to this repository's issues, and the browser window and an uninstall entry lose CrossOver's names. Not for upstream, which uses its own names already. |
| `0004-steam-bridge-loader.patch` | Valve, [ValveSoftware/wine](https://github.com/ValveSoftware/wine) `proton_11.0` at dc26e61, ported to this tree | Valve's Steam bridge: a game's `steamclient` DLL hands its calls to lsteamclient, which talks to the Mac Steam app, so a Windows game bought on Steam runs with one sign-in and no Windows Steam. lsteamclient itself is its own archive. Valve's Windows Steam client run in this engine without lsteamclient needs `PROTON_DISABLE_LSTEAMCLIENT=1`, as in Proton. Not in WineHQ; carried as the one exception in mavrik's upstream-first rule. |
| `0005-makedep-cpp-sources.patch` | Valve, ValveSoftware/wine `proton_11.0` (one table line) | makedep reads `.cpp` sources, so lsteamclient's C++ Unix half builds against this tree with Wine's own make. Changes nothing in the engine's own build: the Wine tree has no C++ file. |
| `0006-game-name-in-the-dock.patch` | this repository, following Chromium, Firefox and WebKit | The Dock and the app switcher showed every game as "wine". The Mac driver now sets the process's LaunchServices display name to the name its app menu already uses (the program's, or `WINEPRELOADERAPPNAME`), with a private call looked up at run time, and processes a game starts keep that name. On a macOS without the call, the name stays "wine". The loader also escapes `&`, `<` and `>` in the name it writes into its Info.plist and never cuts a character in half: CrossOver's hack wrote it raw, and a title such as "Ratchet & Clank" made macOS reject the whole Info.plist. To be offered upstream: the display name to WineHQ, the loader parts to CodeWeavers. Since patch 0007 the display name is the fallback for when no link can be made. |
| `0007-game-name-in-the-menu-bar.patch` | CodeWeavers' CW HACK 22144 (in the CrossOver tree), adapted | The menu bar and Cmd-Tab still showed "wine": macOS's window server takes a program's name only from the file it was started through. CrossOver's hack already starts each Windows program through a link named after it, but only with `WINEDLLPATH` set, through a hard link, and named after the program's file. Here it always runs, makes a symbolic link (so the process's executable stays the loader inside the engine, which a launcher uses to find and stop its processes), takes the name from `WINEPRELOADERAPPNAME` without overwriting it, and makes the name safe (`/` as U+2215, no control characters, cut between whole characters to 31 bytes decomposed, as the window server keeps it). To be offered to CodeWeavers. |
| `0008-dock-floor-only-while-floating.patch` | this repository | Wine keeps every always-on-top window above the Dock even while Wine is not the active app, so a game in exclusive full screen stayed in front of the app the player Cmd-Tabbed to. Only windows the Mac driver puts at a floating level get that floor now; an inactive full-screen window gets the normal level, as Wine's `WindowsFloatWhenInactive` setting intends. To be offered to WineHQ. |
| `0009-coreaudio-period-frame-size.patch` | upstream Wine, commits 56a4347 (Giovanni Mascellani), 07c7fcc, 8e09602 and da0b084 (Zhiyi Zhang), unchanged | Sound in some games was choppy (Rogue Legacy since S180): Wine never set the Mac's audio piece size, so the Mac pulled 512 frames at a time while a game's SDL2 added 480 per 10 ms tick, and the queue ran dry. Upstream Wine now sets the Mac's piece size to Wine's period and reports the real one. Remove when the pinned CrossOver sources carry these commits. |
| `0010-msync-unregister-early-return.patch` | [highball-engine](https://github.com/gauthierpiarrette/highball-engine) `patches/0014-msync-unregister-early-return.patch` (Gauthier Piarrette, LGPL-2.1-or-later), unchanged | mavrik runs every game with MSync (CodeWeavers' Mach-port sync, `WINEMSYNC=1`). A wait on several objects that returned early never took its registration back, and the wineserver's side left object 0 registered when object 1 was signaled, so a rarely signaled object gained a list node per lost race: the 524,288-node pool ran out and the wineserver grew until the Mac ran out of memory (My Summer Car, highball#224). Highball measured it on this same CrossOver 26.3 tree: the wineserver went from 30 MB to 77 MB in 30 s on a reproducer, and stayed at 39 MB for 2 minutes with the fix, with no slower waits. MSync is CrossOver's code, not WineHQ's, so it is offered to CodeWeavers. |
| `0011-wine-mono-11.3.0.patch` | upstream Wine, commits 7674396 (11.0.0), 9f4295c (11.1.0), 2927904 (11.2.0), 2142f77 and 29a87db (11.3.0), all Esme Povirk, unchanged | The tree asks for Wine Mono 11.3.0, the version Wine's master branch asks for, and the engine carries that Mono (the addons gate checks they match). Wine Mono 11 brings FNA 26.08 and SDL 3.4.14 for XNA and FNA games, and WPF, System.Drawing and Visual Basic 6 fixes. Remove when the pinned CrossOver sources ask for this version or a newer one. |
| `0012-faudio-26.10.patch` | upstream Wine, commits 1c8966d (FAudio 26.02), 934f579 (26.06), ed52d49 and 9c5c88a (fixes), 6847401 (26.09) and c23103d (26.10), unchanged | Wine's XAudio2 and XACT run on FAudio 26.10 instead of 25.12: XACT3 wave variations, a resampler crash on small buffer updates, a race when a voice is destroyed, and the WMA path rewritten in 26.06 with its later fix. Every file in `libs/faudio` then equals Wine's at c23103d, except its `Makefile.in` (Wine's new makefiles, not taken) and an unused `stb_vorbis.h` Wine removed. Remove when the pinned CrossOver sources carry FAudio 26.10 or newer. |

## Checked and not needed

- **DXMT's hooks in the Mac driver.** DXMT looks up `macdrv_functions` in `winemac.so` first, and
  only falls back to five separate function names when that is missing. The CrossOver tree already
  exports `macdrv_functions` (`dlls/winemac.drv/d3dmetal.c`, made for D3DMetal and DXMT), and its
  layout matches what DXMT reads (v0.80, and main at 50102f994b). The five fallback names stay hidden, so they need no patch.
  The `winemac` gate checks both the export and the layout on every build.
- **athei/wine's loader check (revision 2's patch 0004, removed in revision 3).** Without it, every
  32-bit program was relaunched through `start.exe`. Wine's own setting `WINEARCH=wow64` does the
  same with no patch: Wine names no alternate loader in that mode, so the program runs in the
  process it starts. mavrik sets it for every Wine program it starts in a game's folder.
- **highball-engine's 0003 (`WINEDLLPATH_PREPEND`).** mavrik puts DXMT's files straight into the
  engine instead of an overlay folder.
- **highball-engine's other patches** fix specific games or measured faults mavrik has not met yet.
  Each can be adopted with its own reason when a mavrik game needs it (0014 was, as 0010, because every
  mavrik game runs with MSync).
